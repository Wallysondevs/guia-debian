Debian KVM e virt-manager

Uma máquina virtual (VM) é um computador inteiro de mentira rodando dentro do seu: com disco, memória, placa de rede e o sistema que você quiser, até Windows. No Linux, o motor é o KVM, que vem no próprio kernel, mais o QEMU, que simula o hardware, e o libvirt, que organiza tudo. O virt-manager é a janela para clicar; o virsh é o comando para o terminal.

Você vai aprender
  • Quem é quem: KVM, QEMU, libvirt, virsh, virt-install e virt-manager.
  • Verificar se o seu processador aguenta VMs rápidas.
  • Instalar no Debian e liberar o acesso para a sua usuária.
  • Ligar a rede default, que no Debian vem desligada.
  • Criar, listar, ligar e apagar VMs pelo terminal.
  • O que é virtualização aninhada, e por que a VM deste guia não a tem.

As saídas vêm do Debian 13 de laboratório (libvirt 11.3.0, QEMU 10.0.13). Esse Debian é, ele mesmo, uma VM do VirtualBox, e isso aparece nos testes.

Passo 1: o processador aguenta?

O KVM precisa das extensões de virtualização do processador: VT-x (Intel) ou AMD-V (AMD). Elas aparecem como vmx ou svm em /proc/cpuinfo.

grep -E -c
-E = expressão regular estendida, -c = só contar as linhas.
'(vmx|svm)'
"vmx ou svm".
/proc/cpuinfo
As informações do processador, uma seção por núcleo.

Num computador de verdade, com a virtualização ligada na BIOS/UEFI (o número é a quantidade de núcleos, e varia):

$ grep -E -c '(vmx|svm)' /proc/cpuinfo
8                                          « maior que zero: tem suporte
$ lscpu | grep Virtualização
Virtualização:                             VT-x
$ ls -l /dev/kvm
crw-rw---- 1 root kvm 10, 232 out 15 08:00 /dev/kvm   « o KVM está pronto

Dentro da VM de laboratório deste guia, a resposta é outra:

$ grep -E -c '(vmx|svm)' /proc/cpuinfo
0                                          « o processador "virtual" não tem as extensões
$ lscpu | grep -E "hipervisor|Tipo de virt"
Fabricante do hipervisor:                  KVM
Tipo de virtualização:                     completo         « eu mesmo sou uma VM
$ systemd-detect-virt
oracle                                     « …do VirtualBox
$ ls -l /dev/kvm
ls: não foi possível acessar '/dev/kvm': Arquivo ou diretório inexistente

A ferramenta pronta: kvm-ok

O pacote cpu-checker traz o kvm-ok, que faz o diagnóstico de uma vez. Ele fica em /usr/sbin, fora do PATH da ana, então rode como root:

#> apt install cpu-checker
#> kvm-ok
INFO: Your CPU does not support KVM extensions
KVM acceleration can NOT be used

Numa máquina com suporte, a resposta é INFO: /dev/kvm exists e KVM acceleration can be used.

$ su -
Senha:

11.3.0

Num servidor sem interface gráfica, deixe o virt-manager de fora: você pode instalá-lo no seu notebook e conectar ao servidor por SSH.

Passo 3: quem pode usar

O libvirt tem duas "conexões":

ConexãoO que éQuem usa
qemu:///systemAs VMs do sistema, gerenciadas pelo serviço; podem usar a rede default e ligar no bootroot e o grupo libvirt
qemu:///sessionVMs particulares do usuário, com recursos limitadosQualquer usuário

Sem grupo, a ana cai na sessão dela, vazia, e não acessa as VMs do sistema:

$ virsh uri
qemu:///session
$ virsh -c qemu:///system list
error: failed to connect to the hypervisor
error: authentication unavailable: no polkit agent available to authenticate action 'org.libvirt.unix.manage'

Para liberar, o root coloca a ana no grupo libvirt (e no kvm, para as VMs da sessão dela usarem o KVM):

#> getent group libvirt kvm
libvirt:x:110:
kvm:x:993:
#> usermod -aG libvirt,kvm ana

Depois de sair e entrar de novo, a ana usa virsh -c qemu:///system …. Para não digitar isso toda vez, acrescente export LIBVIRT_DEFAULT_URI=qemu:///system ao .bashrc.

Atenção: grupo libvirt = poder de root

Quem gerencia VMs do sistema pode montar discos e arquivos do computador dentro delas. Dê o grupo só a quem já administraria a máquina.

Passo 4: a rede default (desligada no Debian)

O libvirt cria uma rede chamada default: uma ponte virbr0 com NAT, em 192.168.122.0/24, que dá internet às VMs. No Ubuntu ela já vem ligada. No Debian, não:

#> virsh net-list --all
 Name      State      Autostart   Persistent
----------------------------------------------
 default   inactive   no          yes                 « inativa e sem início automático
virsh net-start default
Liga a rede agora.
virsh net-autostart default
Liga a rede sozinha a cada boot.
#> virsh net-start default
Network default started

#> virsh net-autostart default
Network default marked as autostarted

#> virsh net-list --all
 Name      State    Autostart   Persistent
--------------------------------------------
 default   active   yes         yes
#> ip -br a show virbr0
virbr0           DOWN           192.168.122.1/24       « DOWN só até a primeira VM se conectar

Esquecer esse passo é a causa número um de "a VM não tem internet" ou de "Network not found: no network with matching name 'default'".

Passo 5: criar uma VM

Pela janela: virt-manager

  1. Abra o Gerenciador de máquinas virtuais pelo menu (ou virt-manager no terminal).
  2. Clique em Criar uma nova máquina virtual e escolha Mídia de instalação local.
  3. Aponte a ISO (por exemplo, a debian-13-amd64-netinst.iso), defina memória, CPUs e disco.
  4. Na última tela, confira a rede: Rede virtual 'default': NAT.

Pelo terminal: virt-install

--name debian-teste
O nome da VM.
--memory 2048 --vcpus 2
2 GB de memória e 2 processadores.
--disk size=20
Cria um disco novo de 20 GB (em /var/lib/libvirt/images).
--cdrom …iso
A ISO de instalação.
--osinfo debian13
Diz o sistema, para o libvirt escolher bons padrões (virt-install --osinfo list mostra os nomes).
--network network=default
Liga a VM à rede default.
#> virt-install --name debian-teste --memory 2048 --vcpus 2 --disk size=20 \
     --cdrom /var/lib/libvirt/images/debian-13-amd64-netinst.iso \
     --osinfo debian13 --network network=default

Para conferir as mensagens reais sem instalar nada, criamos na VM de laboratório uma VM mínima, sem disco e sem rede:

#> virt-install --name teste --memory 256 --vcpus 1 --disk none --network none --pxe --osinfo detect=on,require=off --noautoconsole --graphics none
Iniciando instalação...
Criando o domínio...                                        |         00:00

O domínio ainda está em execução. A instalação pode estar em andamento.
Você pode se reconectar ao console para concluir o processo de instalação.

O virt-install fala português; o virsh, como você vai ver, fala inglês. "Domínio" (domain) é o nome que o libvirt dá às VMs.

Sem KVM: o que acontece?

O libvirt ainda funciona, mas o QEMU passa a simular o processador por software. O virt-host-validate explica:

#> virt-host-validate qemu
  QEMU: Checking for hardware virtualization                                 : FAIL (Host not compatible with KVM; HW virtualization CPU features not found. Only emulated CPUs are available; performance will be significantly limited)
  QEMU: Checking if device '/dev/vhost-net' exists                           : PASS
  QEMU: Checking if device '/dev/net/tun' exists                             : PASS
  QEMU: Checking for cgroup 'cpu' controller support                         : PASS
…
#> virsh capabilities | grep -o "domain type=.[a-z]*." | sort -u
domain type='qemu'                         « só emulação; com KVM, apareceria também domain type='kvm'

Na prática, uma VM emulada é dezenas de vezes mais lenta: serve para testes curtos, não para uso diário.

Virtualização aninhada

Rodar uma VM dentro de outra VM se chama virtualização aninhada. É o caso do Debian de laboratório: ele roda no VirtualBox, que não repassa o VT-x por padrão. No computador de fora:

$ VBoxManage showvminfo debian-guia --machinereadable | grep nested-hw-virt
nested-hw-virt="off"
$ VBoxManage modifyvm debian-guia --nested-hw-virt on       « com a VM desligada

No KVM, o equivalente é o módulo kvm_intel ou kvm_amd com a opção nested=1 no computador de fora.

Quando não funciona

"KVM acceleration can NOT be used" num computador de verdade

O que aconteceu: a virtualização está desligada na BIOS/UEFI (é o mais comum), ou o processador é muito antigo.

Como resolver: reinicie, entre na configuração da placa-mãe e ligue "Intel Virtualization Technology", "VT-x", "SVM Mode" ou "AMD-V".

"Network not found: no network with matching name 'default'" ou VM sem internet

O que aconteceu: no Debian, a rede default vem inativa. Como resolver: virsh net-start default e virsh net-autostart default, como root.

"authentication unavailable: no polkit agent available"

O que aconteceu: a usuária tentou usar qemu:///system sem estar no grupo libvirt. Como resolver: como root, usermod -aG libvirt ana; depois saia e entre de novo.

As VMs criadas pela ana não aparecem no virt-manager (ou o contrário)

O que aconteceu: uma está em qemu:///session e a outra em qemu:///system. São listas separadas. Como confirmar: virsh uri.

VirtualBox e KVM ao mesmo tempo

O que aconteceu: os dois querem o VT-x com exclusividade; uma VM de um deles pode falhar ao ligar enquanto o outro está rodando.

Como resolver: use um de cada vez (desligue as VMs do outro).

Resumo

  • KVM (kernel) + QEMU (hardware) + libvirt (organização) = VMs no Linux.
  • Confira vmx/svm e /dev/kvm; sem eles, só emulação lenta.
  • Instale qemu-system-x86 libvirt-daemon-system virtinst virt-manager como root.
  • Grupo libvirt para gerenciar as VMs do sistema (equivale a root).
  • No Debian, ligue a rede: virsh net-start default e net-autostart default.
