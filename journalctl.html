Debian Logs (journalctl)

Quando algo dá errado (um serviço que não sobe, um login suspeito, um disco com problema), a resposta quase sempre está nos logs: o "diário" em que o sistema anota tudo o que acontece. No Debian 13 esse diário é o journal do systemd, e você o lê com journalctl.

Você vai aprender
  • Por que o Debian 13 não tem mais o /var/log/syslog.
  • Por que a usuária comum vê só uma parte dos logs, e como liberar o resto.
  • Filtrar por serviço, boot, gravidade, horário e palavra.
  • Investigar um serviço que não sobe, do status até a causa.
  • Ver e limitar o espaço que os logs ocupam.

Antes do comando: onde estão os logs no Debian 13

Quem já usou Linux antigo procura o arquivo /var/log/syslog. No Debian 13 ele não existe:

$ ls /var/log/syslog
ls: não foi possível acessar '/var/log/syslog': Arquivo ou diretório inexistente
$ ls /var/log
alternatives.log  apt  btmp  dpkg.log  installer  journal  lastlog  private  README  runit  wtmp  wtmp.db

Desde o Debian 12, o pacote rsyslog, que escrevia os arquivos de texto, não é mais instalado por padrão. Tudo vai para o journal, guardado em formato próprio na pasta /var/log/journal. O próprio Debian deixou um bilhete explicando:

$ cat /var/log/README
You are looking for the traditional text log files in /var/log, and they are
gone?

Here's an explanation on what's going on:

You are running a systemd-based OS where traditional syslog has been replaced
with the Journal. The journal stores the same (and more) information as classic
syslog. To make use of the journal and access the collected log data simply
invoke "journalctl", which will output the logs in the identical text-based
format the syslog files in /var/log used to be.

Como a pasta /var/log/journal existe, o journal é persistente: os logs sobrevivem quando a máquina reinicia. Outros arquivos continuam em /var/log, como o dpkg.log (o que foi instalado) e a pasta apt.

Quero os arquivos de texto de volta

Se você precisa do /var/log/syslog (por exemplo, para uma ferramenta antiga que lê esse arquivo), instale o rsyslog como root: apt install rsyslog. Ele passa a escrever os arquivos de texto, e o journal continua funcionando.

A forma mais simples: journalctl

journalctl
De journal control. Sem opções, mostra todo o diário, do mais antigo ao mais novo, num paginador.

Cada linha tem sempre o mesmo formato:

$ journalctl -n 1
out 15 21:17:01 notebook CRON[11933]: (root) CMD (cd / && run-parts --report /etc/cron.hourly)
PedaçoSignificado
out 15 21:17:01Data e hora (mês traduzido)
notebookNome da máquina
CRON[11933]Quem escreveu e o PID dele
O restoA mensagem, quase sempre em inglês

O paginador é o less: setas para rolar, G para ir ao fim, / para buscar, Q para sair.

A usuária comum vê só os próprios logs

Rode o journalctl como ana e repare no aviso:

$ journalctl -n 3
Hint: You are currently not seeing messages from other users and the system.
      Users in groups 'adm', 'systemd-journal' can see all messages.
      Pass -q to turn off this notice.
out 15 21:10:01 notebook sshd-session[8220]: Disconnected from user ana 192.168.0.20 port 56534
out 15 21:10:09 notebook sshd-session[8314]: Received disconnect from 192.168.0.20 port 40684:11: disconnected by user
out 15 21:10:09 notebook sshd-session[8314]: Disconnected from user ana 192.168.0.20 port 40684

O aviso diz: "você não está vendo mensagens de outros usuários e do sistema; quem está nos grupos adm ou systemd-journal vê tudo". No Debian, a ana não está em nenhum dos dois:

$ groups
ana cdrom floppy audio dip video plugdev users netdev
$ journalctl -u ssh
Hint: You are currently not seeing messages from other users and the system.
      Users in groups 'adm', 'systemd-journal' can see all messages.
      Pass -q to turn off this notice.
-- No entries --                       « os logs do SSH são do sistema: escondidos para a ana

Há duas saídas:

  1. Ler os logs como root (su -, depois journalctl).
  2. Colocar a ana no grupo adm, que é o grupo tradicional de quem lê logs. Como root: 
    #> usermod -aG adm ana
    A mudança vale no próximo login da ana (saia e entre de novo). Veja Usuários e Grupos.
Cuidado com o -a

Sem o -a, o usermod -G adm ana tira a ana de todos os outros grupos. Use sempre -aG.

Nos exemplos a seguir, os comandos rodam como root (prompt #) ou por alguém do grupo adm.

As últimas linhas: -n e -f

Quase sempre você quer o fim do diário, onde está o que acabou de acontecer.

OpçãoOrigemO que faz
-n 20linesSó as últimas 20 linhas, sem paginador
-ffollowFica mostrando as linhas novas ao vivo (sai com Ctrl+C)
-rreverseDo mais novo para o mais antigo
-eendAbre o paginador já no fim

O -f é ótimo para ver um problema acontecendo: deixe um terminal com journalctl -f e, em outro, reinicie o serviço.

Um serviço só: -u

journalctl
O programa.
-u ssh
De unit: só as mensagens do serviço ssh.
-n 3
Só as 3 últimas.
#> journalctl -u ssh -n 3
out 15 21:17:32 notebook sshd-session[12108]: pam_unix(sshd:session): session closed for user root
out 15 21:17:32 notebook sshd-session[12118]: Accepted publickey for root from 192.168.0.20 port 54438 ssh2: ED25519 SHA256:ixgT4QXITUrqe0aI2mG5JqJnP118rAlE94kt7cqMC9E
out 15 21:17:32 notebook sshd-session[12118]: pam_unix(sshd:session): session opened for user root(uid=0) by root(uid=0)

Aqui dá para ler quem entrou: Accepted publickey for root from 192.168.0.20 = alguém entrou como root, de 192.168.0.20, usando chave SSH.

Por boot: -b

#> journalctl --list-boots
IDX BOOT ID                          FIRST ENTRY                 LAST ENTRY
  0 d6d709bc5a41440cbcef012815c2bdbb Thu 2026-10-15 20:55:47 -03 Thu 2026-10-15 21:10:09 -03
#> journalctl -b -1
No journal boot entry found for the specified boot (-1).

-b sozinho é o boot atual; -b -1 é o anterior. Numa máquina que só ligou uma vez, como essa, não há boot anterior. É a ferramenta certa para "o computador travou e reiniciou: o que aconteceu antes?" (veja Quando o Sistema Trava).

Por gravidade: -p

Cada mensagem tem uma prioridade, do mais grave ao mais leve:

NúmeroNomeSignificado
0emergO sistema está inutilizável
1alertAção imediata necessária
2critCrítico
3errErro
4warningAviso
5noticeNormal, mas digno de nota
6infoInformativo
7debugDetalhes para depuração

-p err mostra erros e tudo o que for mais grave (err, crit, alert, emerg):

#> journalctl -b -p err -n 3
out 15 21:09:54 notebook systemd-ssh-generator[8051]: Failed to query local AF_VSOCK CID: Cannot assign requested address
out 15 21:09:55 notebook (e-gia.sh)[8060]: teste-guia.service: Failed at step EXEC spawning /usr/local/bin/teste-gia.sh: No such file or directory
out 15 21:09:56 notebook systemd-ssh-generator[8111]: Failed to query local AF_VSOCK CID: Cannot assign requested address

Nem todo "erro" é problema: a mensagem do systemd-ssh-generator aparece em máquinas virtuais e pode ser ignorada. Já a do teste-guia é um serviço que não conseguiu rodar.

Por horário: --since e --until

#> journalctl -u cron --since "15 min ago"
#> journalctl --since today
#> journalctl --since "2026-10-15 20:00" --until "2026-10-15 21:00"
#> journalctl --since yesterday -p warning

As palavras precisam ser em inglês (today, yesterday, ago):

#> journalctl --since hoje
Failed to parse timestamp: hoje

Por palavra: -g

O -g (de grep) filtra pelo texto da mensagem, aceitando expressão regular:

#> journalctl -u ssh -g "Failed password|Accepted" -n 2
out 15 21:17:32 notebook sshd-session[12118]: Accepted publickey for root from 192.168.0.20 port 54438 ssh2: ED25519 SHA256:ixgT4QXITUrqe0aI2mG5JqJnP118rAlE94kt7cqMC9E
out 15 21:17:32 notebook sshd-session[12108]: Accepted publickey for root from 192.168.0.20 port 54426 ssh2: ED25519 SHA256:ixgT4QXITUrqe0aI2mG5JqJnP118rAlE94kt7cqMC9E

Também dá para usar o grep de sempre num pipe: journalctl -u ssh | grep "Failed password" (veja grep).

Combinando filtros

Os filtros se somam. Leia o comando como uma frase:

journalctl
Mostre o diário...
-u ssh
...do serviço SSH...
-b
...só deste boot...
-p warning
...só avisos ou pior...
--no-pager
...direto na tela, sem paginador.

E o kernel tem um atalho próprio: -k mostra só as mensagens do kernel (o mesmo que o dmesg, mas com data legível):

#> journalctl -k -n 2
out 15 21:16:44 notebook kernel: loop0: detected capacity change from 0 to 4194304
out 15 21:16:45 notebook kernel:  loop0: p1 p2

Cenário completo: o serviço não sobe

Um serviço chamado teste-guia não está funcionando. Siga o roteiro:

  1. O que o status diz? 
    #> systemctl status teste-guia
× teste-guia.service - Serviço de teste do Guia Debian
     Loaded: loaded (/etc/systemd/system/teste-guia.service; static)
     Active: failed (Result: exit-code) since Thu 2026-10-15 21:09:55 -03; 1s ago
    Process: 8060 ExecStart=/usr/local/bin/teste-gia.sh (code=exited, status=203/EXEC)

    Falhou (×) com 203/EXEC: não conseguiu executar o programa.

  2. O que o log diz? 
    #> journalctl -u teste-guia -n 4
out 15 21:09:55 notebook (e-gia.sh)[8060]: teste-guia.service: Unable to locate executable '/usr/local/bin/teste-gia.sh': No such file or directory
out 15 21:09:55 notebook (e-gia.sh)[8060]: teste-guia.service: Failed at step EXEC spawning /usr/local/bin/teste-gia.sh: No such file or directory
out 15 21:09:55 notebook systemd[1]: teste-guia.service: Main process exited, code=exited, status=203/EXEC
out 15 21:09:55 notebook systemd[1]: teste-guia.service: Failed with result 'exit-code'.

    "Unable to locate executable" = o arquivo /usr/local/bin/teste-gia.sh não existe.

  3. Confirmar. 
    #> ls /usr/local/bin/
teste-guia.sh                « o nome certo tem um "u": teste-guia
  4. Corrigir o ExecStart no arquivo do serviço, systemctl daemon-reload e systemctl restart teste-guia. O passo a passo de criar serviços está em Criar um Serviço.

Espaço ocupado pelos logs

#> journalctl --disk-usage
Archived and active journals take up 16M in the file system.
#> journalctl --vacuum-time=30d
Vacuuming done, freed 0B of archived journals from /var/log/journal/03c89c72dc504632b46ffa5cf5f2879b.
Vacuuming done, freed 0B of archived journals from /var/log/journal.

--vacuum-time=30d apaga os arquivos de log com mais de 30 dias; --vacuum-size=500M limita pelo tamanho. Numa máquina nova, como esta, não há nada antigo para apagar (freed 0B).

Por padrão o journal usa no máximo 10% do disco (até 4 GB). Para um limite fixo, como root, crie /etc/systemd/journald.conf.d/tamanho.conf com:

[Journal]
SystemMaxUse=500M

e rode systemctl restart systemd-journald.

Logs são provas

Não apague logs para "economizar espaço" sem pensar. Se a máquina for invadida ou um disco começar a falhar, é neles que você vai descobrir o que aconteceu.

Formas diferentes de ver logs

FormaQuando usar

journalctl -u nome -n 50Investigar um serviço

journalctl -b -1 -p errO que deu errado antes do último reinício

journalctl -o json-prettyVer todos os campos de uma mensagem

Quando não funciona

"Hint: You are currently not seeing messages from other users and the system."

O que aconteceu: você não é root nem está nos grupos adm/systemd-journal, padrão no Debian.

Como resolver: leia como root ou, como root, usermod -aG adm ana e faça login de novo. Para só esconder o aviso, use -q.

"-- No entries --"

O que aconteceu: não há mensagens que combinem com os filtros. Pode ser o nome do serviço errado (o journalctl não avisa que a unit não existe), um horário fora do intervalo, ou o aviso acima (sem permissão para ver).

Como resolver: confira o nome com systemctl list-units | grep nome e tire os filtros um a um.

"Failed to parse timestamp"

O que aconteceu: o --since não entende palavras em português nem datas no formato dia/mês.

Como resolver: use today, yesterday, "1 hour ago" ou "2026-10-15 20:00".

"No journal boot entry found for the specified boot (-1)"

O que aconteceu: não há boot anterior guardado (máquina recém-instalada) ou os logs antigos já foram apagados.

Como resolver: veja os boots disponíveis com journalctl --list-boots.

Exercícios

1. Só o SSH

Complete para ver as 20 últimas linhas do serviço ssh:

journalctl

2. Ao vivo

Qual opção mostra as linhas novas conforme aparecem?

journalctl

3. Liberar os logs para a ana

Complete o comando (como root) que coloca a ana no grupo que lê logs, sem tirá-la dos outros:

usermod ana

4. Num Debian 13 recém-instalado, por que ls /var/log/syslog dá "Arquivo ou diretório inexistente"?

5. O computador reiniciou sozinho. Qual comando mostra os erros de antes do reinício?

Resumo

  • No Debian 13 não há /var/log/syslog: os logs ficam no journal (/var/log/journal), lidos com journalctl.
  • A ana vê só os próprios logs; root ou o grupo adm veem tudo.
  • -u filtra o serviço, -b o boot, -p a gravidade, --since o horário, -g o texto.
  • -n 20 e -f são os mais usados no dia a dia.
  • Serviço com problema: systemctl status diz que falhou; journalctl -u diz por quê.
