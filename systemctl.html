Debian systemctl

Um serviço é um programa que roda o tempo todo em segundo plano, sem janela: o servidor SSH, o agendador de tarefas, um servidor web. Quem liga, desliga e vigia esses serviços no Debian é o systemd, e você conversa com ele pelo comando systemctl.

Você vai aprender
  • O que são systemd, units e serviços.
  • Ler o systemctl status linha por linha.
  • A diferença entre start (agora) e enable (no próximo boot), e o que é mask.
  • Por que, no Debian, a usuária comum consegue ver mas não consegue mudar serviços.
  • Listar serviços rodando, com falha, e os timers agendados.

Antes do comando: systemd e units

Quando o computador liga, o kernel inicia um programa: o systemd. Ele é o processo número 1 (PID 1) e inicia todo o resto, na ordem certa: rede, login, serviços. Depois, continua vigiando: se um serviço cai, ele pode reiniciá-lo. No Debian 13 a versão é a 257:

$ systemctl --version
systemd 257 (257.13-1~deb13u1)

Cada coisa que o systemd gerencia é uma unit ("unidade"), descrita num arquivo de texto. O tipo aparece no fim do nome:

TipoO que éExemplo no Debian
.serviceUm programa (serviço)ssh.service, cron.service
.timerUm agendamento, como o cronapt-daily.timer, logrotate.timer
.socketUma porta que liga o serviço quando alguém conectadbus.socket
.mountUm disco montadotmp.mount (o /tmp em memória)
.targetUm grupo de units, um "estágio" do bootmulti-user.target, graphical.target

Quando você omite o tipo, o systemctl assume .service: systemctl status cron é o mesmo que systemctl status cron.service.

"Daemon"

Programas de serviço são chamados de daemons, e muitos têm nome terminado em d: sshd, systemd, journald. Veja o Glossário.

     Loaded: loaded (/etc/systemd/system/teste-guia.service; static)

O status diz que falhou. Para descobrir por quê, leia o log com journalctl -u teste-guia. A investigação completa está em Criar um Serviço e Logs (journalctl).

Ligar, desligar e reiniciar

Estas ações mudam o sistema, então precisam de root. No Debian instalado com senha de root não existe sudo: entre como root com su - (veja root, su e sudo). Os exemplos com root@notebook:~# foram digitados assim.

systemctl
O programa.
restart
A ação: parar e iniciar de novo.
ssh
O serviço.
$ su -
Senha:
#> systemctl restart ssh
#> systemctl is-active ssh
active

Como quase todo comando, o restart não mostra nada quando dá certo. Por isso conferimos com is-active.

E se a ana tentar sem ser root?

$ systemctl restart cron
Failed to restart cron.service: Access denied
See system logs and 'systemctl status cron.service' for details.
$ echo $?
4

No Ubuntu Desktop, o sistema abriria uma janela pedindo senha (é o polkit). Num Debian servidor o polkit não vem instalado, então a resposta é direta: acesso negado. A mensagem do systemctl não tem tradução e fica em inglês.

AçãoO que fazQuando usar
startIniciaO serviço está parado
stopParaVocê quer desligar agora
restartPara e iniciaDepois de mudar a configuração
reloadRelê a configuração sem pararServiços que suportam (ssh, nginx); não derruba conexões
reload-or-restartreload se der, senão restartQuando você não sabe se o serviço suporta reload
Cuidado com o SSH num servidor remoto

Um systemctl stop ssh feito por SSH derruba a sua própria porta de entrada. Para aplicar mudanças no sshd_config, prefira reload e mantenha a sessão atual aberta até testar uma nova conexão.

Ligar no boot: enable, disable e mask

start liga agora; enable liga no próximo boot. São coisas independentes. No Debian, muitos serviços antigos também têm um script SysV, e o systemctl avisa que está sincronizando os dois:

#> systemctl disable cron
Synchronizing state of cron.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
Executing: /usr/lib/systemd/systemd-sysv-install disable cron
Removed '/etc/systemd/system/multi-user.target.wants/cron.service'.      « o "atalho" do boot foi apagado
#> systemctl is-enabled cron
disabled
#> systemctl enable cron
Synchronizing state of cron.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
Executing: /usr/lib/systemd/systemd-sysv-install enable cron
Created symlink '/etc/systemd/system/multi-user.target.wants/cron.service' → '/usr/lib/systemd/system/cron.service'.

Repare no que o enable faz por baixo: cria um link simbólico dentro de multi-user.target.wants/. Quando o boot chega ao estágio multi-user.target, o systemd liga tudo o que tiver um link ali.

systemctl
O programa.
enable
Liga no boot.
--now
E também liga agora (junta enable e start).
cron
O serviço.

mask: proibir de vez

Um serviço disabled ainda pode ser ligado na mão, ou por outro serviço que dependa dele. O mask (máscara) aponta a unit para /dev/null e impede qualquer partida:

#> systemctl mask cron
Created symlink '/etc/systemd/system/cron.service' → '/dev/null'.
#> systemctl start cron
Failed to start cron.service: Unit cron.service is masked.
#> systemctl unmask cron
Removed '/etc/systemd/system/cron.service'.
EstadoLiga no boot?Dá para ligar na mão?
enabledSimSim
disabledNãoSim
staticNão por conta própria; outra unit chamaSim
maskedNãoNão

O que o comando devolve: perguntas para scripts

Três ações só respondem uma pergunta, com uma palavra e um código de saída:

$ systemctl is-active ssh
active
$ systemctl is-enabled ssh
enabled
$ systemctl is-active nada
inactive
$ echo $?
4                                       « 4 = essa unit não existe
Códigois-active
0Está rodando
3Existe, mas está parada (inactive)
4Unit inexistente

Com isso, um script decide o que fazer (veja Condicionais):

#!/usr/bin/env bash
if systemctl is-active --quiet ssh; then
  echo "SSH no ar"
else
  echo "SSH parado!"
fi

Ver o arquivo de um serviço

$ systemctl cat cron
# /usr/lib/systemd/system/cron.service
[Unit]
Description=Regular background program processing daemon
Documentation=man:cron(8)
After=remote-fs.target nss-user-lookup.target

[Service]
EnvironmentFile=-/etc/default/cron
ExecStart=/usr/sbin/cron -f $EXTRA_OPTS
IgnoreSIGPIPE=false
KillMode=process
Restart=on-failure

Os arquivos que vêm nos pacotes ficam em /usr/lib/systemd/system/ e não devem ser editados: uma atualização sobrescreveria. Os seus ficam em /etc/systemd/system/, que tem prioridade. Para mudar só uma opção de um serviço do sistema, use systemctl edit cron (como root): ele cria um arquivo extra só com a sua mudança.

Quando não funciona

"Unit nada.service could not be found." 
$ systemctl status nada
Unit nada.service could not be found.

O que aconteceu: não há serviço com esse nome. Às vezes o nome é outro: no Debian o servidor SSH é ssh (e não sshd), e o Apache é apache2.

Como resolver: procure com systemctl list-unit-files | grep -i parte-do-nome.

"Failed to restart …: Access denied"

O que aconteceu: você tentou mudar um serviço como usuária comum.

Como resolver: rode como root (su -) ou com su -c "systemctl restart cron".

"The unit file … changed on disk" 
#> systemctl start teste-guia
Warning: The unit file, source configuration file or drop-ins of teste-guia.service changed on disk. Run 'systemctl daemon-reload' to reload units.

O que aconteceu: você editou o arquivo do serviço e o systemd ainda está usando a versão antiga, que ficou na memória.

Como resolver: systemctl daemon-reload e depois o restart.

"Unit … is masked."

O que aconteceu: alguém (ou um pacote) mascarou o serviço para impedir que ele rode.

Como resolver: se for isso mesmo que você quer ligar, systemctl unmask nome e depois start.

O serviço aparece como failed

Como resolver: leia o log do serviço: journalctl -u nome -n 30. O passo a passo está em Logs (journalctl).

Resumo

  • O systemd (PID 1) liga e vigia as units; o systemctl conversa com ele.
  • status qualquer um vê; start, stop, restart, enable exigem root (no Debian, via su -).
  • start é agora, enable é no boot, mask proíbe.
  • is-active e is-enabled servem para scripts (código 0, 3 ou 4).
  • Editou um arquivo de unit? systemctl daemon-reload.
