Debian Segurança do Servidor

Um servidor ligado à internet recebe tentativas de invasão minutos depois de ir ao ar. A boa notícia: no Debian, as defesas mais importantes são poucas e simples. Atualizações em dia, SSH só com chave, um firewall e alguém de olho nas tentativas de login. Esta aula mostra cada uma, com o que o Debian 13 já traz e o que você precisa ligar.

Você vai aprender
  • Como o Debian publica correções de segurança (Security Team, DSA, repositório trixie-security).
  • Verificar vulnerabilidades com debsecan.
  • Instalar e ativar o unattended-upgrades, que no Debian não vem ligado.
  • Endurecer o SSH e banir quem insiste com o fail2ban.
  • Conferir o AppArmor, que já vem ativo.

Os comandos são como root na máquina servidor (su -). As saídas vêm de um Debian 13 real.

Os princípios

  1. Atualizar. A maioria das invasões explora falhas que já têm correção publicada.
  2. Menos portas abertas. Só o necessário fica acessível de fora (Firewall (nftables)).
  3. Menos privilégio. Trabalhe como usuário comum e vire root só quando precisar (root, su e sudo).
  4. Autenticação forte. SSH com chave, sem senha.
  5. Olhar os logs. Saber quem tentou entrar.

Como o Debian entrega correções de segurança

O Debian tem uma equipe de segurança (Debian Security Team). Quando uma falha é corrigida, ela publica:

  • O pacote corrigido no repositório trixie-security, que já está no seu /etc/apt/sources.list:
$ grep security /etc/apt/sources.list
deb http://security.debian.org/debian-security trixie-security main non-free-firmware
deb-src http://security.debian.org/debian-security trixie-security main non-free-firmware
  • Um aviso chamado DSA (Debian Security Advisory), com o pacote, a falha (o número CVE) e a versão corrigida. Os DSAs saem na lista de e-mail debian-security-announce e no site www.debian.org/security.

Ou seja: para ficar protegido, basta instalar as atualizações. O Debian estável não muda versões de programas no meio do caminho; ele aplica só a correção. Por isso atualizar o Debian estável é seguro e raramente quebra algo.

debsecan: quais falhas me afetam?

O debsecan (de Debian Security Analyzer) compara os pacotes instalados com o banco de dados de falhas do Debian. Instale com apt install debsecan.

debsecan
O programa.
--suite trixie
Qual versão do Debian você usa.
--only-fixed
Mostra só as falhas que já têm correção disponível. São essas que você precisa resolver.
#> debsecan --suite trixie --only-fixed
#> echo $?
0                                           « nada: tudo o que tem correção já foi instalado
#> debsecan --suite trixie | head -4
CVE-2026-103658 aspell                      « falhas conhecidas, ainda sem correção publicada
CVE-2026-75818 aspell
CVE-2026-75819 aspell
CVE-2026-3184 bsdextrautils

A lista completa (sem --only-fixed) é longa e assusta, mas ela inclui falhas pequenas, falhas que não afetam a configuração padrão e falhas que ainda não têm correção. O que importa no dia a dia é a saída do --only-fixed estar vazia.

unattended-upgrades: atualizações sozinhas

No Debian instalado sem interface gráfica, o unattended-upgrades (atualizações "sem supervisão") não vem instalado. E, mesmo depois de instalar, ele não roda até você ativar. São três passos:

  1. Instalar: apt install unattended-upgrades.
  2. Ativar: dpkg-reconfigure -plow unattended-upgrades e responder Sim à pergunta sobre baixar e instalar atualizações estáveis automaticamente.
  3. Conferir os arquivos e testar com --dry-run.

Logo depois de instalar, o serviço aparece como habilitado, mas falta o arquivo que liga a rotina diária:

#> systemctl is-enabled unattended-upgrades
enabled
#> cat /etc/apt/apt.conf.d/20auto-upgrades
cat: /etc/apt/apt.conf.d/20auto-upgrades: Arquivo ou diretório inexistente       « ainda não está ativado

O dpkg-reconfigure cria esse arquivo com duas linhas:

APT::Periodic::Update-Package-Lists "1";   // atualizar a lista de pacotes todo dia
APT::Periodic::Unattended-Upgrade "1";     // instalar as atualizações todo dia

O que ele instala sozinho está em /etc/apt/apt.conf.d/50unattended-upgrades. Estas são as linhas ativas no Debian 13:

Unattended-Upgrade::Origins-Pattern {
        "origin=Debian,codename=${distro_codename},label=Debian";                    // as revisões estáveis (13.x)
        "origin=Debian,codename=${distro_codename},label=Debian-Security";
        "origin=Debian,codename=${distro_codename}-security,label=Debian-Security";  // as de segurança
};
Unattended-Upgrade::Package-Blacklist {
};

Para testar sem instalar nada, use --dry-run (ensaio). Se outro apt estiver rodando, ele desiste, como nesta saída real:

#> unattended-upgrade --dry-run -v
Iniciando o script da atualização desacompanhada
O lock não pôde ser obtido (outro gerenciador de pacotes em funcionamento?)
O lock do cache não pode ser obtido, encerrando

Com o apt livre, ele lista as origens (São origens permitidas: …) e o que instalaria. O registro das execuções fica em /var/log/unattended-upgrades/.

Reinício depois das atualizações

Atualizações do kernel ou de bibliotecas só valem depois de reiniciar o programa (ou a máquina). O needrestart verifica isso; veja Manutenção.

Endurecer o SSH

Estas são as configurações efetivas do SSH num Debian 13 recém-instalado. O sshd -T mostra todas, já com os padrões aplicados:

#> sshd -T | grep -Ei "^(permitrootlogin|passwordauthentication|pubkeyauthentication|x11forwarding) "
permitrootlogin without-password          « root entra só com chave, nunca com senha
pubkeyauthentication yes
passwordauthentication yes                « usuários comuns podem entrar com senha
x11forwarding yes

O Debian já impede o root de entrar com senha (without-password é o mesmo que prohibit-password). O passo seguinte é tirar a senha de todo mundo, depois que a sua chave estiver funcionando (veja SSH).

Não edite o arquivo principal: crie um arquivo seu em /etc/ssh/sshd_config.d/, que vem vazio no Debian e é lido primeiro:

PasswordAuthentication no      # só chave
PermitRootLogin no             # root nem com chave: entre como ana e use su -
X11Forwarding no               # servidor não precisa de janelas gráficas
MaxAuthTries 3                 # menos tentativas por conexão
#> sshd -t                       « confere a sintaxe: silêncio = tudo certo
#> systemctl reload ssh
Teste antes de fechar a sessão

Depois do reload, abra uma nova conexão SSH numa segunda janela. Só feche a primeira se a segunda entrar. Com PermitRootLogin no, lembre que no Debian o seu usuário pode não ter sudo: confirme que você sabe a senha do root para usar su -.

Quem tentou entrar?

O Debian 13 não tem /var/log/auth.log (não há rsyslog). Os logins ficam no journal:

#> journalctl -u ssh -n 3 --no-pager
out 15 21:11:59 servidor sshd-session[9771]: Accepted publickey for root from 192.168.0.15 port 43002 ssh2: ED25519 SHA256:ixgT4QXITUrqe0aI2mG5JqJnP118rAlE94kt7cqMC
out 15 21:11:59 servidor sshd-session[9771]: pam_unix(sshd:session): session opened for user root(uid=0) by root(uid=0)
out 15 21:12:01 servidor sshd-session[9809]: pam_unix(sshd:session): session opened for user root(uid=0) by root(uid=0)

As tentativas que falharam aparecem como Failed password for … ou Invalid user …. Para contar: journalctl -u ssh --since today | grep -c "Failed password".

fail2ban: banir quem insiste

O fail2ban lê os logs e, quando um endereço erra a senha várias vezes, cria uma regra de firewall bloqueando esse endereço por um tempo. No Debian 13 o pacote já vem pronto para o jeito Debian: lê o journal (não o auth.log) e bane com nftables. Este é o arquivo que o pacote instala:

[DEFAULT]
banaction = nftables                          # bane criando regras no nftables
banaction_allports = nftables[type=allports]

[sshd]
backend = systemd                             # lê o journal do systemd
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd
enabled = true                                # a proteção do SSH já vem ligada
#> apt install fail2ban
#> fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed:	0
|  |- Total failed:	0
|  `- Journal matches:	_SYSTEMD_UNIT=ssh.service + _COMM=sshd
`- Actions
   |- Currently banned:	0
   |- Total banned:	0
   `- Banned IP list:

Os valores padrão são 5 tentativas (maxretry) em 10 minutos para banir por 10 minutos (bantime). Para mudar, crie /etc/fail2ban/jail.local:

[sshd]
maxretry = 3
bantime = 1h
ignoreip = 127.0.0.1/8 192.168.0.0/24    # nunca banir a rede de casa

Para desbanir um endereço: fail2ban-client set sshd unbanip 203.0.113.50. A saída do status acima é a típica do fail2ban 1.1.

O fail2ban não bane ninguém

O que aconteceu: em configurações antigas (copiadas da internet), o [sshd] aponta para /var/log/auth.log, que não existe no Debian 13. A linha Journal matches do status mostra se ele está lendo o journal.

Como resolver: no seu jail.local, use backend = systemd e apague qualquer logpath = /var/log/auth.log.

AppArmor: limitar o que cada programa pode fazer

O AppArmor prende programas a uma lista do que eles podem acessar (um perfil). Mesmo que alguém invada o programa, ele não sai dessa lista. No Debian ele vem ativo desde o Debian 10:

#> aa-status
apparmor module is loaded.
105 profiles are loaded.
6 profiles are in enforce mode.          « enforce: as regras são aplicadas
   /usr/bin/man
   lsb_release
   man_filter
   man_groff
   nvidia_modprobe
   nvidia_modprobe//kmod
23 profiles are in complain mode.        « complain: só registra, não bloqueia
…
0 processes have profiles defined.

Pacotes como nginx, cups e o libvirt trazem perfis próprios. Para ferramentas extras de AppArmor (como aa-enforce e aa-complain), instale o pacote apparmor-utils.

Checklist do servidor Debian novo

  1. Atualize: apt update && apt full-upgrade.
  2. Crie seu usuário (se o provedor só deu root) com adduser ana, e decida: sudo (apt install sudo + usermod -aG sudo ana) ou su - com a senha do root.
  3. Chave SSH: do seu computador, ssh-copy-id ana@servidor; teste o login.
  4. Endureça o SSH com o arquivo em sshd_config.d; teste numa segunda sessão.
  5. Firewall: /etc/nftables.conf com SSH liberado; nft -c -f; systemctl enable --now nftables.
  6. Atualizações automáticas: apt install unattended-upgrades + dpkg-reconfigure -plow unattended-upgrades.
  7. fail2ban: apt install fail2ban e confira fail2ban-client status sshd.
  8. Revise as portas abertas: ss -tulpn (veja ip, ping, ss).

Quando não funciona

"O lock não pôde ser obtido"

O que aconteceu: outro apt (seu, ou a rotina automática apt-daily) estava rodando. O unattended-upgrade desiste e tenta na próxima vez.

Como confirmar: ps aux | grep -E "apt|dpkg".

Instalei o unattended-upgrades e nada é atualizado

O que aconteceu: falta o /etc/apt/apt.conf.d/20auto-upgrades. Rode dpkg-reconfigure -plow unattended-upgrades.

Depois de mexer no SSH, "Permission denied (publickey)"

O que aconteceu: você desligou a senha antes de a chave funcionar. Pelo console do provedor (ou fisicamente), apague o seu arquivo em sshd_config.d e rode systemctl reload ssh.

Resumo

  • O Debian corrige falhas pelo trixie-security e avisa com DSAs; debsecan --only-fixed mostra o que falta.
  • unattended-upgrades precisa ser instalado e ativado com dpkg-reconfigure.
  • SSH: arquivo próprio em sshd_config.d, sshd -t, teste numa segunda sessão.
  • fail2ban no Debian 13 já lê o journal e bane com nftables.
  • AppArmor vem ativo; confira com aa-status.
