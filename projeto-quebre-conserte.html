Projeto Quebre e Conserte

Cedo ou tarde um servidor não liga, uma senha some ou o disco enche. Quem já consertou isso uma vez num laboratório resolve em minutos na vida real. Neste projeto você estraga um Debian 13 de propósito, seis vezes, e aprende a trazê-lo de volta.

Ao terminar você terá
  • Saído do modo de emergência causado por um /etc/fstab errado.
  • Trocado a senha do root sem saber a antiga, pelo GRUB.
  • Recuperado o acesso de administrador quando não há sudo nem senha de root.
  • Achado e limpado o que encheu o disco.
  • Descoberto por que o Apache não sobe, lendo a mensagem certa.
  • Consertado a rede pelo console, sem SSH.

Estes desafios deixam o sistema sem iniciar, sem rede ou sem administrador. Faça na sua VM de laboratório e tire um snapshot antes de cada um:

$ VBoxManage snapshot lab take antes-do-desafio

Se você se perder, desligue a VM e restaure: VBoxManage snapshot lab restore antes-do-desafio (veja Como Usar os Projetos). Vários desafios exigem a janela da VM (o console), porque o SSH para de funcionar.

Sobre as saídas desta página

As telas de boot e de erro abaixo são as típicas do Debian 13. Números de tempo, UUIDs e nomes de interface mudam de máquina para máquina. Algumas mensagens de boot aparecem em inglês mesmo com o sistema em português, porque não têm tradução.

Desafio 1: o fstab errado e o modo de emergência

  1. Quebre

    Vamos pedir ao sistema que monte um disco que não existe. Primeiro, a cópia de segurança. Depois, a linha errada no fim do /etc/fstab:

    $ su -
Senha:
#> cp /etc/fstab /etc/fstab.bak
#> echo 'UUID=0000-errado  /dados  ext4  defaults  0  2' >> /etc/fstab
#> mkdir /dados
#> systemctl reboot

  2. Sintoma

    Na janela da VM, o boot fica parado 1min30 esperando o disco e depois cai no modo de emergência:

    [ ***  ] A start job is running for /dev/disk/by-uuid/0000-errado (1min 12s / 1min 30s)
[ TIME ] Timed out waiting for device dev-disk-by\x2duuid-0000\x2derrado.device - /dev/disk/by-uuid/0000-errado.
[DEPEND] Dependency failed for dados.mount - /dados.
[DEPEND] Dependency failed for local-fs.target - Local File Systems.
You are in emergency mode. After logging in, type "journalctl -xb" to view
system logs, "systemctl reboot" to reboot, or "exit"
to continue bootup.
Give root password for maintenance
(ou pressione Contrl-D para continuar):          « o "Contrl" errado está na tradução original

    Repare: o sistema não quebrou. Ele parou de propósito porque uma montagem marcada como necessária falhou, e está pedindo a senha do root para você consertar.

  3. Diagnóstico

    Digite a senha do root (nada aparece enquanto digita). Você cai num shell de root. Pergunte ao sistema o que falhou:

    #> systemctl --failed
  UNIT       LOAD   ACTIVE SUB    DESCRIPTION
● dados.mount loaded failed failed /dados

#> findmnt --verify
/media/cdrom0
   [W] não foi possível detectar o tipo de sistema de arquivos em disco (Mídia não encontrada)
/dados
   [E] fonte não alcançável na inicialização: UUID=0000-errado     « o culpado
0 erro de análise, 1 erro, 1 aviso

    O findmnt --verify lê o /etc/fstab e aponta a linha com problema sem precisar montar nada. Os [E] são erros; os [W], avisos. O aviso do /media/cdrom0 é inofensivo: o instalador do Debian deixa essa linha para o leitor de CD, que numa VM normalmente está vazio.

  4. Conserte

    Volte à cópia de segurança (ou apague a linha com o nano) e confira de novo antes de reiniciar:

    #> cp /etc/fstab.bak /etc/fstab
#> findmnt --verify
/media/cdrom0
   [W] não foi possível detectar o tipo de sistema de arquivos em disco (Mídia não encontrada)

0 erro de análise, 0 erro, 1 aviso     « sem erros: pode reiniciar
#> systemctl daemon-reload
#> systemctl reboot

    Confira se deu certo: o boot volta ao normal e systemctl --failed mostra 0 loaded units listed.

    Se deu errado: "Read-only file system" ao editar

    Em alguns casos a raiz está montada só para leitura. Remonte com escrita e tente de novo: mount -o remount,rw /.

  5. Lição

    • Para discos que não são essenciais (HD externo, disco de backup), use a opção nofail no fstab. Sem o disco, o boot continua. O findmnt --verify continua avisando que a fonte não foi encontrada, mas o boot não para mais.
    • Antes de reiniciar depois de editar o fstab, rode sempre findmnt --verify e mount -a.

Desafio 2: esqueci a senha do root

  1. Quebre

    Troque a senha do root por uma que você "não lembra":

    #> passwd
Nova senha:
Redigite a nova senha:
passwd: senha atualizada com sucesso

    Digite qualquer coisa aleatória duas vezes, não anote, saia e tente su -:

    $ su -
Senha:
su: Falha de autenticação

  2. Conserte pelo GRUB: init=/bin/bash

    A ideia: pedir ao kernel que, em vez de iniciar o sistema normal (o systemd), abra direto um shell de root. Sem login, sem senha.

    1. Reinicie a VM pela janela do VirtualBox. No menu do GRUB, com Debian GNU/Linux selecionado, aperte e (editar).
    2. Desça até a linha que começa com linux. Vá até o fim dela e acrescente init=/bin/bash.
    3. Aperte Ctrl+X (ou F10) para iniciar.
    linux   /boot/vmlinuz-6.12.111+deb13-amd64 root=UUID=5c1f…  ro  quiet init=/bin/bash
                                                                  « acrescente no fim da linha

    Você cai num shell de root mínimo. A raiz está montada só para leitura, então primeiro libere a escrita:

    mount -o remount,rw /
    Remonta a raiz (/) com permissão de escrita (read-write).
    passwd
    Troca a senha do usuário atual, o root.
    sync
    Força a gravação de tudo no disco, porque não haverá um desligamento normal.
    #> mount -o remount,rw /
#> passwd
New password:                    « sem o systemd, o idioma não foi carregado: as mensagens vêm em inglês
Retype new password:
passwd: password updated successfully
#> sync
#> exec /sbin/reboot -f

    Confira se deu certo: depois do boot normal, su - aceita a senha nova.

    Se deu errado: "Authentication token manipulation error"

    Você esqueceu o mount -o remount,rw /, e o passwd não conseguiu gravar em /etc/shadow. Remonte e repita.

  3. Lição

    Quem tem acesso ao console (físico ou da VM) consegue virar root. Em servidores de verdade, proteja com senha no GRUB e criptografia de disco (LUKS, oferecida pelo instalador do Debian).

Desafio 3: sem sudo e sem senha de root

Este desafio vale para a instalação "estilo Ubuntu": no instalador do Debian você deixou a senha do root em branco. Aí o root fica bloqueado e o primeiro usuário entra no grupo sudo. Para fazer o desafio, crie uma segunda VM assim, ou use a do Servidor Web, onde a ana ganhou sudo.

  1. Quebre

    A ana tira a si mesma do grupo sudo. Ninguém mais administra a máquina:

    $ sudo gpasswd -d ana sudo
Removendo usuário ana do grupo sudo
$ exit

    Entre de novo (a mudança de grupo só vale num login novo) e tente:

    $ sudo ls /root
[sudo] senha para ana:
ana is not in the sudoers file.
This incident has been reported to the administrator.

    O pedido de senha sai em português e a recusa em inglês: é assim mesmo no sudo do Debian 13.

  2. Por que o modo de recuperação não ajuda

    No GRUB, Advanced options for Debian GNU/Linux > (recovery mode) pede a senha do root. Com o root bloqueado, ele avisa e não deixa entrar:

    Cannot open access to console, the root account is locked.
See sulogin(8) man page for more details.

Press Enter to continue.

  3. Conserte com init=/bin/bash

    Mesmo caminho do desafio 2: e no GRUB, init=/bin/bash no fim da linha linux, Ctrl+X. No shell:

    #> mount -o remount,rw /
#> usermod -aG sudo ana
#> grep '^sudo:' /etc/group
sudo:x:27:ana
#> sync
#> exec /sbin/reboot -f

    Confira se deu certo: depois de entrar, groups mostra sudo na lista e sudo -v pede a senha da ana e aceita.

  4. Lição

    • Nunca use usermod -G sem o -a: ele substitui todos os grupos, e você perde o sudo sem perceber.
    • Antes de mexer nos próprios grupos ou no /etc/sudoers, deixe outro terminal com sudo -i aberto.
    • Para editar regras do sudo, use sempre visudo, que confere a sintaxe antes de salvar.

Desafio 4: disco cheio

  1. Quebre

    O fallocate cria um arquivo grande instantaneamente. Vamos criar um que ocupa todo o espaço livre:

    fallocate -l
    Reserva espaço para um arquivo, do tamanho (length) indicado.
    $(df --output=avail -B1 / | tail -1)
    O espaço livre da raiz, em bytes, calculado pelo df.
    /var/tmp/enchedor
    Um nome qualquer, num lugar onde ninguém procura.
    #> fallocate -l $(df --output=avail -B1 / | tail -1) /var/tmp/enchedor

  2. Sintoma

    Coisas estranhas começam a falhar, e para um usuário comum a mensagem é sempre a mesma:

    $ cp /etc/services ~/teste
cp: erro de escrita de '/home/ana/teste': Não há espaço disponível no dispositivo
$ df -h /
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda1        19G   18G     0 100% /
    Por que o root ainda consegue gravar?

    O ext4 reserva 5% do disco para o root, justamente para o sistema não travar de vez. Por isso serviços que rodam como root às vezes continuam funcionando um pouco mais.

  3. Diagnóstico

    Do geral para o detalhe: primeiro qual pasta de nível 1 é grande, depois dentro dela.

    du
    Mede o espaço usado (disk usage).
    -x
    Fica no mesmo sistema de arquivos (não conta /proc, /sys…).
    -h
    Tamanhos legíveis.
    -d 1 /
    Só um nível abaixo da raiz.
    | sort -h
    Ordena pelos tamanhos legíveis, maior por último.
    #> du -xh -d 1 / 2>/dev/null | sort -h | tail -4
212M	/var/cache                « não, esse fica em /var
1,3G	/usr
16G	/var                      « o culpado está aqui dentro
18G	/
#> du -xh -d 1 /var | sort -h | tail -3
212M	/var/cache
16G	/var/tmp
16G	/var
#> ls -lh /var/tmp
total 16G
-rw-r--r-- 1 root root 16G out 15 21:40 enchedor

  4. Conserte

    #> rm /var/tmp/enchedor
#> apt clean
#> journalctl --vacuum-size=100M
Vacuuming done, freed 0B of archived journals from /var/log/journal.
#> df -h /
Sist. Arq.      Tam. Usado Disp. Uso% Montado em
/dev/sda1        19G  1,6G   17G   9% /

    Confira se deu certo: df -h / volta a mostrar espaço livre e o cp funciona.

    Se deu errado: apaguei um arquivo grande e o espaço não voltou

    Algum programa ainda está com o arquivo aberto (um log que um serviço continua escrevendo). O espaço só volta quando ele fecha. Ache com lsof +L1 (pacote lsof) e reinicie o serviço dono do arquivo.

  5. Lição

    Os vilões de sempre num Debian: /var/log e o journal, /var/cache/apt (limpe com apt clean), kernels antigos (apt autoremove), imagens de container (/var/lib/docker) e arquivos esquecidos em /var/tmp. Veja lsblk, df, du.

Desafio 5: o serviço que não sobe

Precisa do Apache instalado (feito no Servidor Web do Zero).

  1. Quebre

    Um erro de digitação, como acontece de verdade: DocumentRoot vira DocumentRot.

    $ sudo sed -i 's/DocumentRoot/DocumentRot/' /etc/apache2/sites-available/000-default.conf
$ sudo systemctl restart apache2
Job for apache2.service failed because the control process exited with error code.
See "systemctl status apache2.service" and "journalctl -xeu apache2.service" for details.

  2. Diagnóstico

    A própria mensagem diz onde olhar. Mas o caminho mais rápido é pedir ao Apache para conferir a configuração:

    $ sudo apache2ctl configtest
AH00526: Syntax error on line 12 of /etc/apache2/sites-enabled/000-default.conf:
Invalid command 'DocumentRot', perhaps misspelled or defined by a module not included in the server configuration

    Tudo o que você precisa: o arquivo, a linha (12) e a palavra errada. O journalctl mostra a mesma coisa, com data:

    $ sudo journalctl -u apache2 -n 5 --no-pager

  3. Conserte

    $ sudo sed -i 's/DocumentRot /DocumentRoot /' /etc/apache2/sites-available/000-default.conf
$ sudo apache2ctl configtest
Syntax OK
$ sudo systemctl restart apache2
$ systemctl is-active apache2
active

  4. Lição

    Antes de reiniciar um serviço depois de editar a configuração, teste-a: apache2ctl configtest, nginx -t, sshd -t, visudo -c, nft -c -f. Um teste de dois segundos evita derrubar o site.

Desafio 6: a rede caiu e o SSH junto

  1. Quebre

    Troque o nome da interface no /etc/network/interfaces por um que não existe e reinicie a rede. A sessão SSH vai congelar: é o esperado. Faça pela janela da VM ou aceite perder o SSH.

    #> cp /etc/network/interfaces /etc/network/interfaces.bak
#> sed -i 's/enp0s3/enp9s9/g' /etc/network/interfaces
#> systemctl restart networking

  2. Sintoma

    O SSH para de responder. Do seu computador:

    $ ssh -p 2222 ana@127.0.0.1
kex_exchange_identification: read: Connection reset by peer

  3. Diagnóstico, pelo console da VM

    Entre como root na janela do VirtualBox e compare o nome real da interface com o do arquivo:

    #> ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s3           DOWN                                     « a placa existe, mas está sem IP
#> grep -n enp /etc/network/interfaces
11:allow-hotplug enp9s9
12:iface enp9s9 inet dhcp

  4. Conserte

    #> cp /etc/network/interfaces.bak /etc/network/interfaces
#> ifup enp0s3
#> ip -br a show enp0s3
enp0s3           UP             10.0.2.15/24 fe80::a00:27ff:fe4e:66a1/64

    Confira se deu certo: o ssh -p 2222 ana@127.0.0.1 volta a funcionar.

  5. Lição

    • Mexer na rede de um servidor remoto sem acesso ao console é pedir para viajar até ele. Em servidores na nuvem, descubra antes onde fica o "console serial" do provedor.
    • Os nomes das placas no Debian são previsíveis (enp0s3, ens18…) e aparecem em ip -br a. Copie de lá, não digite de memória.
    • Tenha sempre uma cópia .bak antes de editar um arquivo de configuração.

Checklist do que você aprendeu

  • findmnt --verify e nofail evitam o modo de emergência por causa do fstab.
  • init=/bin/bash no GRUB abre um shell de root sem senha; depois, mount -o remount,rw /.
  • Com o root bloqueado, o modo de recuperação não abre; o init=/bin/bash continua funcionando.
  • Disco cheio: df -h para ver, du -xh -d 1 | sort -h para achar.
  • Serviço que não sobe: teste a configuração (apache2ctl configtest) e leia o journalctl -u.
  • Rede caída: console da VM, ip -br a, compare com /etc/network/interfaces, ifup.

Desafios extras

  • Proteja o GRUB com senha (grub-mkpasswd-pbkdf2) e veja o desafio 2 deixar de funcionar.
  • Apague o kernel em uso por engano (numa VM com snapshot!) e recupere com um pendrive live e chroot. Veja Recuperar um Sistema.
  • Deixe um processo usando 100% de CPU (yes > /dev/null &), ache com top e encerre com kill.

Limpeza

O jeito mais rápido é restaurar o snapshot tirado no começo:

$ VBoxManage controlvm lab poweroff
$ VBoxManage snapshot lab restore antes-do-desafio

Resumo

  • Quebrar de propósito num laboratório com snapshot é o melhor treino para emergências reais.
  • Quase todo problema de boot se resolve com o console, a senha do root (ou init=/bin/bash) e a leitura da mensagem de erro.
  • Teste antes de aplicar: findmnt --verify, apache2ctl configtest, visudo -c, nft -c.
