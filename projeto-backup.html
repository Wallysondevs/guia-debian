Projeto Backup Automático

Um backup que depende de você lembrar não é backup. E um backup que nunca foi restaurado é só uma esperança. Neste laboratório você monta, num Debian 13, uma rotina que copia os dados todo dia sozinha, guarda 7 dias de histórico sem gastar espaço à toa, avisa quando falha e, o mais importante, prova que a restauração funciona.

Ao terminar você terá
  • Um script /usr/local/bin/backup-dados.sh que copia /srv/dados com rsync para uma pasta com data e hora.
  • Cópias diárias que compartilham os arquivos repetidos (--link-dest): 7 dias de histórico ocupando pouco mais que uma cópia.
  • Um log em /var/log/backup-dados.log.
  • Um systemd timer rodando às 02:00, e um aviso no journal quando o backup falhar.
  • Uma restauração testada: de um arquivo e da pasta inteira.

No mundo real

Aqui o destino /backup fica no mesmo disco, para simplificar. Na vida real ele deve ser outro disco (um HD externo montado em /backup, outro servidor). Backup no mesmo disco não sobrevive a um disco queimado. Veja a regra 3-2-1 em Backup.

As etapas

  1. Virar root e instalar o rsync

    O que vamos fazer e por quê: o backup lê e grava em pastas do sistema, então tudo aqui roda como root. No Debian instalado com senha de root, o caminho é su -. O rsync nem sempre vem na instalação mínima.

    $ su -
Senha:
#> apt install rsync
#> rsync --version | head -1
rsync  version 3.5.0  protocol version 32

    Confira: a última linha mostra a versão. Se aparecer bash: rsync: comando não encontrado, a instalação não terminou.

  2. Criar os dados de exemplo

    O que vamos fazer e por quê: precisamos de algo para proteger. Dois textos (fáceis de conferir) e um arquivo de 1 MB, simulando uma foto.

    #> mkdir -p /srv/dados/docs /srv/dados/fotos
#> echo "contrato da padaria" > /srv/dados/docs/contrato.txt
#> echo "lista de clientes" > /srv/dados/docs/clientes.txt
#> head -c 1048576 /dev/urandom > /srv/dados/fotos/foto1.jpg
#> find /srv/dados
/srv/dados
/srv/dados/docs
/srv/dados/docs/clientes.txt
/srv/dados/docs/contrato.txt
/srv/dados/fotos
/srv/dados/fotos/foto1.jpg

    /srv é a pasta que o Debian reserva para dados servidos pela máquina. Veja Estrutura de Diretórios.

  3. Escrever o script

    O que vamos fazer e por quê: um script reúne os passos e pode ser chamado pelo timer. Crie o arquivo com nano /usr/local/bin/backup-dados.sh:

    #!/bin/bash
# Backup diário de /srv/dados para /backup, com rotação de 7 dias.
set -euo pipefail

ORIGEM="/srv/dados"
DESTINO="/backup"
LOG="/var/log/backup-dados.log"
DATA="$(date +%F_%H%M%S)"

log() { echo "$(date '+%F %T') $*" >> "$LOG"; }

# 1. Sem origem, não há o que copiar: falha com mensagem clara
if [ ! -d "$ORIGEM" ]; then
    log "ERRO: a origem $ORIGEM não existe"
    exit 1
fi

mkdir -p "$DESTINO"
rm -rf "$DESTINO"/.parcial-*          # restos de execuções que falharam
ANTERIOR="$(ls -1d "$DESTINO"/20* 2>/dev/null | tail -n 1 || true)"
PARCIAL="$DESTINO/.parcial-$DATA"

log "início -> $DESTINO/$DATA"

# 2. Copia para uma pasta temporária; arquivos iguais aos do backup
#    anterior viram links (--link-dest) e não ocupam espaço de novo
if [ -n "$ANTERIOR" ]; then
    rsync -a --delete --link-dest="$ANTERIOR" "$ORIGEM/" "$PARCIAL/" >> "$LOG" 2>&1
else
    rsync -a --delete "$ORIGEM/" "$PARCIAL/" >> "$LOG" 2>&1
fi

# 3. Só vira backup "de verdade" se o rsync terminou sem erro
mv "$PARCIAL" "$DESTINO/$DATA"

# 4. Apaga cópias com mais de 7 dias
find "$DESTINO" -mindepth 1 -maxdepth 1 -type d -name '20*' -mtime +7 -exec rm -rf {} +

log "OK $DESTINO/$DATA"

    As partes que merecem atenção:

    TrechoPor quê
    set -euo pipefailPara o script no primeiro erro. Sem isso, um rsync que falhou seria seguido de "OK" no log.
    if [ ! -d "$ORIGEM" ]Se a pasta de dados sumir (disco desmontado, por exemplo), o script avisa em vez de criar um backup vazio.
    .parcial-… e depois mvA cópia só ganha o nome definitivo quando terminou bem. Um backup pela metade nunca vira "o mais recente".
    --link-dest="$ANTERIOR"Arquivos que não mudaram viram hard links para o backup anterior: aparecem inteiros em cada pasta, mas ocupam espaço uma vez só.
    find … -mtime +7 … rm -rfA rotação: apaga as pastas com mais de 7 dias.
    #> chmod 755 /usr/local/bin/backup-dados.sh
#> bash -n /usr/local/bin/backup-dados.sh && echo "sintaxe ok"
sintaxe ok

    O bash -n lê o script sem executar e acusa erros de digitação como um fi esquecido.

  5. Agendar com um systemd timer

    O que vamos fazer e por quê: um .service diz o que rodar; um .timer diz quando. Comparado ao cron, o timer guarda o histórico no journal e, com Persistent=true, roda o backup atrasado se a máquina estava desligada às 02:00.

    [Unit]
Description=Backup diário de /srv/dados
OnFailure=backup-falhou.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup-dados.sh
    [Unit]
Description=Roda o backup todo dia às 02:00

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target

    O OnFailure= chama outro serviço quando o backup falha. Ele grava um aviso de prioridade "erro" no journal:

    [Unit]
Description=Aviso de falha do backup

[Service]
Type=oneshot
ExecStart=/usr/bin/logger -p user.err -t backup "ATENÇÃO: o backup de /srv/dados FALHOU. Veja: journalctl -u backup-dados"
    #> systemctl daemon-reload
#> systemctl enable --now backup-dados.timer
Created symlink '/etc/systemd/system/timers.target.wants/backup-dados.timer' → '/etc/systemd/system/backup-dados.timer'.
#> systemctl list-timers backup-dados.timer
NEXT                            LEFT LAST PASSED UNIT               ACTIVATES
Fri 2026-10-16 02:00:00 -03 4h 16min -         - backup-dados.timer backup-dados.service

1 timers listed.
Pass --all to see loaded but inactive timers, too.

    A coluna NEXT é a próxima execução e LEFT, quanto falta. As datas do systemd saem em inglês (Fri = sexta), mesmo com o sistema em português.

    Confira: rode o serviço na hora, sem esperar as 02:00:

    #> systemctl start backup-dados.service
#> systemctl status backup-dados.service --no-pager
○ backup-dados.service - Backup diário de /srv/dados
     Loaded: loaded (/etc/systemd/system/backup-dados.service; static)
     Active: inactive (dead) since Thu 2026-10-15 21:43:38 -03; 31ms ago
TriggeredBy: ● backup-dados.timer
    Process: 110168 ExecStart=/usr/local/bin/backup-dados.sh (code=exited, status=0/SUCCESS)   « status=0: deu certo
   Main PID: 110168 (code=exited, status=0/SUCCESS)

    inactive (dead) parece ruim, mas é o normal para um Type=oneshot: ele roda, termina e fica parado até a próxima vez. O que importa é o status=0/SUCCESS.

    Se deu errado: "Unit backup-dados.timer has a bad unit file setting"

    Algum erro de digitação nos arquivos. O systemd-analyze verify /etc/systemd/system/backup-dados.* aponta a linha. Depois de corrigir, rode systemctl daemon-reload de novo.

  6. Provocar uma falha e ver o aviso

    O que vamos fazer e por quê: um alarme que nunca tocou pode estar quebrado. Vamos "sumir" com a origem e rodar o backup.

#> systemctl start backup-dados.service

#> journalctl -u backup-dados.service -n 5 --no-pager

out 15 21:43:39 lab systemd[1]: backup-dados.service: Main process exited, code=exited, status=1/FAILURE
out 15 21:43:39 lab systemd[1]: backup-dados.service: Failed with result 'exit-code'.
out 15 21:43:39 lab systemd[1]: Failed to start backup-dados.service - Backup diário de /srv/dados.
out 15 21:43:39 lab systemd[1]: backup-dados.service: Triggering OnFailure= dependencies.   « chamou o aviso
#> journalctl -t backup -n 1 --no-pager
out 15 21:43:39 lab backup[110197]: ATENÇÃO: o backup de /srv/dados FALHOU. Veja: journalctl -u backup-dados
#> tail -1 /var/log/backup-dados.log
2026-10-15 21:45:14 ERRO: a origem /srv/dados não existe
#> mv /srv/dados-x /srv/dados

    O reset-failed limpa o estado de falha, para o systemctl --failed não continuar listando o serviço.

    Ir além: aviso por e-mail

    Troque o ExecStart do backup-falhou.service por um comando que mande e-mail (por exemplo, com o pacote msmtp-mta configurado) ou uma mensagem para um aplicativo de chat via curl.

  7. O teste que importa: restaurar

    O que vamos fazer e por quê: apagar um arquivo "sem querer" e trazê-lo de volta. Depois, restaurar a pasta inteira num lugar separado e comparar tudo.

    #> rm /srv/dados/docs/contrato.txt
#> ls /backup
2026-10-15_214513  2026-10-15_214514
#> rsync -av /backup/2026-10-15_214514/docs/contrato.txt /srv/dados/docs/
sending incremental file list
contrato.txt

sent 129 bytes  received 35 bytes  109,33 bytes/sec
total size is 20  speedup is 0,12
#> cat /srv/dados/docs/contrato.txt
contrato da padaria

    Agora a restauração completa, numa pasta de teste (nunca por cima dos dados de produção sem conferir antes):

    #> mkdir /tmp/restaura
#> rsync -a /backup/2026-10-15_214514/ /tmp/restaura/
#> diff -r /srv/dados /tmp/restaura && echo "IGUAIS"
IGUAIS

    O diff -r compara as duas árvores arquivo por arquivo. Silêncio seguido de IGUAIS é o melhor resultado possível.

    Se deu errado: a pasta de backup mais recente estava vazia

    Foi exatamente esse problema que nos fez criar a etapa .parcial. Numa primeira versão deste script, sem a checagem da origem nem a pasta temporária, um backup com a origem ausente criava uma pasta com a data de hoje vazia. Na hora de restaurar, "o mais recente" não tinha nada. Moral: teste a restauração depois de cada mudança no script.

  8. Conferir a rotação

    Para não esperar uma semana, "envelhecemos" a cópia mais antiga com o touch -d:

    #> touch -d "10 days ago" /backup/2026-10-15_214513
#> ls -l --time-style=+%F /backup
total 8
drwxr-xr-x 4 root root 4096 2026-10-05 2026-10-15_214513
drwxr-xr-x 4 root root 4096 2026-10-15 2026-10-15_214514
#> /usr/local/bin/backup-dados.sh
#> ls /backup
2026-10-15_214514  2026-10-15_214515

    A pasta "de 10 dias" sumiu e uma nova chegou. A rotação funciona.

Checklist do que você aprendeu

  • rsync -a --delete espelha uma pasta; --link-dest cria cópias diárias baratas com hard links.
  • Grave numa pasta temporária e renomeie no fim: um backup pela metade nunca parece completo.
  • Um .service Type=oneshot + um .timer com Persistent=true substituem o cron com vantagens.
  • OnFailure= transforma falhas em avisos.
  • Backup só é backup depois de uma restauração testada com diff -r.

Desafios extras

  • Mande o backup para outra máquina: rsync -a … usuario@servidor:/backup/… com chave SSH (veja SSH).
  • Monte um HD externo em /backup com nofail no fstab e faça o script falhar se ele não estiver montado (mountpoint -q /backup).
  • Experimente o restic (apt install restic): backup com criptografia e deduplicação.

Limpeza

#> systemctl disable --now backup-dados.timer

#> rm /etc/systemd/system/backup-dados.{service,timer} /etc/systemd/system/backup-falhou.service

Resumo

  • Script + rsync --link-dest + timer do systemd = backup diário com histórico, sem trabalho manual.
  • Proteja o script contra os dois piores casos: origem ausente e cópia pela metade.
  • Teste a falha (o aviso aparece?) e a restauração (diff -r dá iguais?).
