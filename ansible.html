Debian Ansible

Configurar um servidor à mão é fácil. Configurar dez servidores do mesmo jeito, e lembrar daqui a um ano o que foi feito, não é. O Ansible resolve isso: você descreve o estado que quer ("o pacote tal instalado, o usuário tal criado, o serviço tal ativo") num arquivo de texto, e ele chega lá, em uma máquina ou em cem, por SSH.

Você vai aprender
  • As peças do Ansible: máquina de controle, inventário, módulo, tarefa e playbook.
  • Rodar comandos avulsos (ad-hoc) e um playbook completo.
  • Testar antes com --check e --diff.
  • O que é idempotência, e por que rodar duas vezes não estraga nada.
  • Como o Ansible vira root num Debian sem sudo.

Tudo nesta página foi rodado no Debian 13 de laboratório, com ansible-core 2.19.11, contra a própria máquina (localhost).

Um playbook, linha por linha

- name: Prepara a máquina do jeito da equipe   # o "play": um nome…
  hosts: locais                                # …e para quais hosts
  tasks:
    - name: Instala ferramentas                # cada tarefa tem um nome legível
      ansible.builtin.apt:                     # módulo apt
        name: [tree, ncdu]
        state: present                         # "presente": instale se faltar
        lock_timeout: 3000                     # espera o apt liberar (padrão: 60 s)

    - name: Cria o usuário deploy
      ansible.builtin.user:
        name: deploy
        shell: /bin/bash

    - name: Cria a pasta do app
      ansible.builtin.file:
        path: /opt/app
        state: directory
        owner: deploy
        mode: "0755"                           # entre aspas: senão o YAML lê como número

    - name: Escreve o aviso
      ansible.builtin.copy:
        dest: /opt/app/LEIAME.txt
        content: "Servidor gerenciado pelo Ansible. Não edite à mão.\n"

    - name: Garante o cron rodando e ativo no boot
      ansible.builtin.service:
        name: cron
        state: started
        enabled: true
YAML: a indentação é tudo

Use sempre espaços (nunca Tab) e alinhe os níveis. Um espaço a mais ou a menos muda o significado ou dá erro de sintaxe.

#> ansible-playbook -i inventario.ini maquina.yml

TASK [Instala ferramentas] *****************************************************
ok: [localhost]
TASK [Cria o usuário deploy] ***************************************************
ok: [localhost]

ok: [localhost]

PLAY RECAP *********************************************************************
localhost                  : ok=6    changed=0    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0

Na segunda vez, tudo aparece como ok e changed=0. Isso é idempotência: o Ansible compara o estado atual com o pedido e só mexe no que falta. Rodar o mesmo playbook de novo, todo dia, é seguro, e é assim que você corrige uma máquina que alguém alterou à mão.

Virar root num Debian sem sudo: become

Instalar pacotes e criar usuários exige root. Quando o Ansible entra num servidor como usuário comum, ele precisa "virar" root, o que se chama become. O padrão é usar sudo, mas num Debian instalado com senha de root ele não existe. Diga ao Ansible para usar o su:

- name: Configura os servidores web
  hosts: web
  become: true            # vire root nas tarefas
  become_method: su       # usando su, como no Debian sem sudo
$ ansible-playbook -i inventario.ini web.yml --ask-become-pass
BECOME password:          « a senha do root dos servidores
Situação do servidorConfiguração
Debian com senha de root, sem sudobecome_method: su + --ask-become-pass (senha do root)
Usuário no grupo sudobecome: true (método padrão) + -K (senha do usuário)
Entrar direto como root por SSH com chaveansible_user=root, sem become

Quando não funciona

"Could not find the requested service" no --check 
#> ansible-playbook -i inventario.ini servidor.yml --check
…
TASK [Garante que o nginx está rodando e ativo no boot] ************************
[ERROR]: Task failed: Module failed: Could not find the requested service nginx: host
…
fatal: [localhost]: FAILED! => {"changed": false, "msg": "Could not find the requested service nginx: host"}

O que aconteceu: no modo de teste, a tarefa anterior só fingiu instalar o nginx. Na tarefa seguinte, o serviço ainda não existe.

Como resolver: é uma limitação do --check, não do playbook. Rode de verdade numa máquina de teste, ou acrescente ignore_errors: "{{ ansible_check_mode }}" nessa tarefa.

Tarefa do apt falha por causa da trava

O que aconteceu: outro apt estava rodando (atualização automática, outro admin) e o módulo desistiu depois de 60 segundos, o padrão.

Como resolver: acrescente lock_timeout: 600 (ou mais) na tarefa ansible.builtin.apt, como no playbook desta página.

"Missing sudo password" / "sudo: comando não encontrado"

O que aconteceu: o playbook usa become com o método padrão (sudo) num Debian sem sudo.

Como resolver: become_method: su e --ask-become-pass com a senha do root.

"UNREACHABLE! … Permission denied (publickey)"

O que aconteceu: o Ansible não conseguiu entrar por SSH. Como confirmar: ssh usuário@host manualmente. Como resolver: copie sua chave com ssh-copy-id (veja SSH).

Resumo

  • Inventário = quem; playbook = o que; módulo = como.
  • Teste com --check --diff antes de aplicar.
  • Idempotência: rodar de novo só mexe no que mudou.
  • No Debian sem sudo: become_method: su + --ask-become-pass.
  • ansible-core do Debian basta para começar.
