Debian Bancos de Dados

Quase toda aplicação guarda seus dados num banco de dados: cadastros, pedidos, posts. No Debian, os dois mais usados vêm prontos no repositório: o PostgreSQL e o MariaDB (o substituto livre do MySQL, que o Debian instala até quando você pede "mysql").

Você vai aprender
  • O que é um servidor de banco de dados e como ele "conversa" com os programas.
  • PostgreSQL: instalar, ver o cluster com pg_lsclusters, criar usuário e banco, usar o psql e fazer backup.
  • MariaDB: entrar como root sem senha (e por quê), criar usuário com senha, consultar e fazer backup.
  • Liberar o acesso de outra máquina sem abrir uma porta perigosa.

Comandos de administração como root (su -) na máquina fictícia servidor; comandos de uso como ana. As saídas vêm de um Debian 13 real com PostgreSQL 17.11 e MariaDB 11.8.6. Os dois respondem em português quando o sistema está em pt-BR, com exceções que a aula mostra.

Conceito: um servidor dentro do servidor

O banco de dados é um serviço que fica rodando e esperando conexões, como o nginx. Os programas não abrem os arquivos do banco: eles se conectam ao serviço e mandam comandos em SQL ("me dê os produtos mais baratos que 10 reais").

PostgreSQL

Instalar e conferir

#> apt install postgresql
#> pg_lsclusters
Ver Cluster Port Status Owner    Data directory              Log file
17  main    5432 online postgres /var/lib/postgresql/17/main /var/log/postgresql/postgresql-17-main.log

O pg_lsclusters é uma ferramenta do Debian. Ela mostra cada cluster (uma instância do PostgreSQL com seus bancos): versão 17, nome main, porta 5432, ligado (online), onde ficam os dados e o log. O Debian deixa ter várias versões e clusters lado a lado, o que facilita atualizar.

O serviço "exited" é normal

systemctl status postgresql mostra active (exited). É um serviço "guarda-chuva" do Debian que liga os clusters. O que de fato roda é o postgresql@17-main: confira com systemctl status postgresql@17-main.

Entrar como administrador

Na instalação, o PostgreSQL cria o usuário de sistema postgres, que é o administrador do banco. Ele entra sem senha porque o Debian usa a autenticação peer: o banco confia no usuário do Linux que está conectando pelo socket local.

#> su - postgres -c "psql -c 'SELECT version();'"
                                                       version
---------------------------------------------------------------------------------------------------------------------
 PostgreSQL 17.11 (Debian 17.11-0+deb13u1) on x86_64-pc-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit
(1 linha)

Se a ana tentar entrar antes de existir um usuário (no PostgreSQL, "role") com o nome dela:

$ psql
psql: erro: a conexão com o servidor no soquete "/var/run/postgresql/.s.PGSQL.5432" falhou: FATAL:  role "ana" não existe

Criar usuário e banco

createuser ana
Cria um "role" (usuário do banco) com o mesmo nome do usuário do Linux, para o peer funcionar.
createdb -O ana loja
Cria o banco loja com -O (owner, dono) ana.
#> su - postgres -c "createuser ana"
#> su - postgres -c "createdb -O ana loja"

Agora a ana usa o próprio banco:

$ psql -d loja -c 'CREATE TABLE produtos (id serial PRIMARY KEY, nome text, preco numeric(10,2));'
CREATE TABLE
$ psql -d loja -c "INSERT INTO produtos (nome, preco) VALUES ('Café', 18.90), ('Pão', 7.50);"
INSERT 0 2                                                « 2 linhas inseridas
$ psql -d loja -c 'SELECT * FROM produtos;'
 id | nome | preco
----+------+-------
  1 | Café | 18.90
  2 | Pão  |  7.50
(2 linhas)

Backup e restauração

$ pg_dump loja > loja.sql                              « exporta o banco inteiro em SQL
$ head -3 loja.sql
--
-- PostgreSQL database dump
--
$ createdb loja_copia
$ psql -q -d loja_copia -f loja.sql                  « recria tudo num banco novo
$ psql -d loja_copia -c 'SELECT count(*) FROM produtos;'
 count
-------
     2
(1 linha)

Para a ana criar um banco, o role dela precisa da permissão: su - postgres -c "createuser --createdb ana", ou o postgres cria por ela.

O root entra sem senha: por quê?

No Debian, o usuário root do MariaDB usa autenticação por socket Unix: o banco confere que quem conecta é o root do Linux e deixa entrar, sem senha. Por isso basta digitar mariadb como root. Qualquer outro usuário do Linux é barrado:

#> mariadb -e "SELECT VERSION();"
VERSION()
11.8.6-MariaDB-0+deb13u1 from Debian
#> mariadb -e "SELECT user, host FROM mysql.user;"
User	Host
mariadb.sys	localhost
mysql	localhost
root	localhost
$ mariadb
ERROR 1698 (28000): Access denied for user 'ana'@'localhost'

Isso é mais seguro do que uma senha de root: ninguém de fora consegue entrar como root, nem adivinhando. Por isso, ao rodar o mariadb-secure-installation (o nome novo do antigo mysql_secure_installation, que nem existe mais no Debian 13), mantenha o root com socket.

Criar banco e usuário para a aplicação

Aplicações (como um site em PHP) conectam com usuário e senha. Crie um usuário só para elas, com acesso só ao banco delas:

#> mariadb
MariaDB [(none)]> CREATE DATABASE loja;
MariaDB [(none)]> CREATE USER 'lojaapp'@'localhost' IDENTIFIED BY 'SenhaForte123';
MariaDB [(none)]> GRANT ALL PRIVILEGES ON loja.* TO 'lojaapp'@'localhost';
MariaDB [(none)]> exit
'lojaapp'@'localhost'
No MariaDB, um usuário é sempre nome@de-onde. localhost = só desta máquina.
IDENTIFIED BY '…'
A senha.
GRANT ALL PRIVILEGES ON loja.*
Todas as permissões, mas só nas tabelas (.*) do banco loja.
$ mariadb -u lojaapp -p loja
Enter password:
MariaDB [loja]> CREATE TABLE produtos (id INT AUTO_INCREMENT PRIMARY KEY, nome VARCHAR(50), preco DECIMAL(10,2));
MariaDB [loja]> INSERT INTO produtos (nome, preco) VALUES ('Café', 18.90), ('Pão', 7.50);
MariaDB [loja]> SELECT * FROM produtos;
+----+------+-------+
| id | nome | preco |
+----+------+-------+
|  1 | Café | 18.90 |
|  2 | Pão  |  7.50 |
+----+------+-------+
2 rows in set (0.001 sec)

O -p sem nada depois faz ele pedir a senha sem mostrá-la (mais seguro que digitar -pSenha, que fica no histórico). As mensagens do MariaDB ficam em inglês.

Backup e restauração

#> mariadb-dump loja > loja.sql
#> head -2 loja.sql
/*M!999999\- enable the sandbox mode */
-- MariaDB dump 10.19-11.8.6-MariaDB, for debian-linux-gnu (x86_64)
#> mariadb loja < loja.sql                               « restaura

O mysqldump e o mysql continuam existindo no Debian como nomes alternativos, para scripts antigos.

Acesso remoto, com cuidado

Por padrão, os dois só aceitam conexões da própria máquina:

#> ss -tlnp | grep -E ":5432|:3306"
LISTEN 0      200        127.0.0.1:5432       0.0.0.0:*    users:(("postgres",pid=139257,fd=7))
LISTEN 0      80         127.0.0.1:3306       0.0.0.0:*    users:(("mariadbd",pid=139580,fd=28))
LISTEN 0      200            [::1]:5432          [::]:*    users:(("postgres",pid=139257,fd=6))

Isso é o certo para a maioria dos casos: a aplicação roda no mesmo servidor. Se outra máquina realmente precisar acessar:

  • Melhor opção: não abra a porta. Use um túnel SSH a partir da outra máquina: ssh -L 5432:localhost:5432 ana@servidor (veja SSH).
  • PostgreSQL: em /etc/postgresql/17/main/postgresql.conf, troque #listen_addresses = 'localhost' por listen_addresses = '*'; em pg_hba.conf, libere só a rede necessária (ex.: host loja ana 192.168.0.0/24 scram-sha-256); reinicie com systemctl restart postgresql.
  • MariaDB: em /etc/mysql/mariadb.conf.d/50-server.cnf, mude bind-address = 127.0.0.1; crie o usuário com o host certo ('lojaapp'@'192.168.0.%'); reinicie.
  • Em qualquer caso, libere a porta no firewall só para o IP de quem precisa (veja Firewall).
Nunca exponha o banco para a internet inteira

Bancos expostos são alvo de robôs que tentam senhas o dia todo. Prefira túnel SSH ou VPN (veja WireGuard).

Parar os serviços

Se o banco era só para estudo, desligue-o para economizar memória:

#> systemctl disable --now postgresql mariadb
Removed '/etc/systemd/system/multi-user.target.wants/postgresql.service'.
Removed '/etc/systemd/system/multi-user.target.wants/mariadb.service'.

Quando não funciona

PostgreSQL: "FATAL: role … não existe" 
$ psql
psql: erro: a conexão com o servidor no soquete "/var/run/postgresql/.s.PGSQL.5432" falhou: FATAL:  role "ana" não existe

O que aconteceu: o psql tenta entrar com um usuário do banco com o mesmo nome do usuário do Linux, e ele não existe.

Como resolver: su - postgres -c "createuser ana", ou entre como administrador: su - postgres -c psql.

PostgreSQL: "FATAL: banco de dados … não existe" 
$ psql -d nada
psql: erro: a conexão com o servidor no soquete "/var/run/postgresql/.s.PGSQL.5432" falhou: FATAL:  banco de dados "nada" não existe

Como resolver: veja os bancos com psql -l e use o nome certo, ou crie com createdb. Sem -d, o psql procura um banco com o seu nome de usuário.

Erro de sintaxe no SQL 
$ psql -d loja -c 'SELEC * FROM produtos;'
ERRO:  erro de sintaxe em ou próximo a "SELEC"
LINHA 1: SELEC * FROM produtos;
         ^                                              « o ^ aponta onde ele se perdeu
#> mariadb loja -e "SELEC * FROM produtos"
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version for the right syntax to use near 'SELEC * FROM produtos' at line 1

Como resolver: a mensagem mostra o trecho do problema (aqui, SELECT escrito errado). No psql, o ^ aponta a posição.

MariaDB: "ERROR 1698 … Access denied" e "ERROR 1045 … (using password: YES)" 
$ mariadb
ERROR 1698 (28000): Access denied for user 'ana'@'localhost'
$ mariadb -u lojaapp -perrada loja
ERROR 1045 (28000): Access denied for user 'lojaapp'@'localhost' (using password: YES)

O que aconteceu: o 1698 aparece quando o usuário entra pelo socket sem ter permissão (a ana não existe no MariaDB); o 1045, quando a senha está errada.

Como resolver: para administrar, entre como root do Linux (su - e mariadb). Para a aplicação, confira o usuário, a senha e o host com SELECT user, host FROM mysql.user;.

"mysql_secure_installation: comando não encontrado"

Como resolver: no Debian 13 o nome é mariadb-secure-installation.

Resumo

  • Debian 13: PostgreSQL 17 (postgresql) e MariaDB 11.8 (mariadb-server), ambos ouvindo só na própria máquina.
  • PostgreSQL: administrador é o usuário postgres; pg_lsclusters mostra os clusters; autenticação peer liga usuário do Linux ao do banco.
  • MariaDB: root entra pelo socket, sem senha; aplicações usam um usuário próprio com GRANT só no banco delas.
  • Backup: pg_dump e mariadb-dump. Acesso remoto: prefira túnel SSH ou VPN.
