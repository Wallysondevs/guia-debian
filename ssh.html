Debian SSH

O SSH (de Secure Shell, "terminal seguro") abre um terminal de outra máquina dentro do seu, com tudo criptografado. É assim que se administra quase todo servidor Debian do mundo: o servidor fica numa sala ou na nuvem, sem tela, e você digita os comandos de longe.

Você vai aprender
  • Instalar e conferir o servidor SSH no Debian.
  • Fazer a primeira conexão e entender a pergunta sobre a "impressão digital".
  • Criar uma chave, copiá-la para o servidor e entrar sem senha.
  • Encurtar os comandos com o ~/.ssh/config.
  • Por que o root do Debian não entra com senha, e como ler os erros mais comuns.

Nos exemplos, a Ana está no notebook e acessa a máquina servidor (192.168.0.50), onde também tem a conta ana. As saídas foram conferidas num Debian 13 real.

Repare que o prompt mudou de ana@notebook para ana@servidor: todo comando agora roda lá. Para voltar, digite exit ou aperte Ctrl+D.

O que é a pergunta "Are you sure…?"

Cada servidor tem uma chave de máquina, e a impressão digital (fingerprint) é um resumo dela. Na primeira conexão, o seu computador ainda não conhece essa chave e pergunta se pode confiar. Respondendo yes, ela é guardada em ~/.ssh/known_hosts. Nas próximas vezes, o SSH confere sozinho e só reclama se a chave mudar.

Para ter certeza absoluta, compare com a impressão digital vista no próprio servidor (pelo console):

$ ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:2cYtXRUqFptnhM0jv3iLXRqpdarrvAHhWD8DsuQKQ5k root@servidor (ED25519)
known_hosts embaralhado no Debian

O Debian liga a opção HashKnownHosts yes (em /etc/ssh/ssh_config). Por isso o ~/.ssh/known_hosts não mostra os nomes das máquinas, só linhas como |1|kM3…=|Xf9…= ssh-ed25519 AAAA…. Assim, quem roubar o arquivo não descobre a quais servidores você se conecta. Para procurar uma máquina nele, use ssh-keygen -F 192.168.0.50; para apagar, ssh-keygen -R 192.168.0.50.

Rodar um comando só

Coloque o comando depois do endereço: o SSH conecta, roda, mostra a saída e volta.

$ ssh ana@192.168.0.50 'uptime; df -h / | tail -1'
 21:20:30 up 25 min,  1 user,  load average: 0,12, 0,10, 0,05
/dev/sda1        24G  1,5G   21G   7% /

Entrar sem senha: chaves

Senhas podem ser adivinhadas. Uma chave é um par de arquivos: a privada fica só com você; a pública vai para os servidores. Quem tem a privada entra. É mais seguro e mais prático.

  1. Crie o par de chaves no notebook (uma vez só):
    ssh-keygen
    Gera chaves.
    -t ed25519
    O tipo: ed25519 é moderno, curto e recomendado.
    -C "ana@notebook"
    Um comentário para reconhecer a chave depois.
    $ ssh-keygen -t ed25519 -C "ana@notebook"

  2. Copie a pública para o servidor com o ssh-copy-id. Ele pede a senha uma última vez: 
    $ ssh-copy-id ana@192.168.0.50
/usr/bin/ssh-copy-id: INFO: Source of key(s) to be installed: "/home/ana/.ssh/id_ed25519.pub"

and check to make sure that only the key(s) you wanted were added.
  3. Teste: agora o SSH não pede a senha da conta (se você criou a chave com frase, pede a frase da chave). 
    $ ssh ana@192.168.0.50 hostname
servidor

No servidor, a chave foi parar em ~/.ssh/authorized_keys, e o ssh-copy-id já deixou as permissões certas:

$ ls -ld ~/.ssh ~/.ssh/authorized_keys
drwx------ 2 ana ana 4096 out 15 21:18 /home/ana/.ssh                    « 700: só a dona entra
-rw------- 1 ana ana   94 out 15 21:18 /home/ana/.ssh/authorized_keys    « 600: só a dona lê

E o log do servidor registra o login por chave (como root, veja Logs):

#> journalctl -u ssh -n 2 --no-pager
out 15 21:06:46 servidor sshd-session[2931]: Accepted publickey for ana from 192.168.0.15 port 44796 ssh2: ED25519 SHA256:iy8XCBgnLtZXtSSjqJ5Cn/s1B+VSIdPlmdwFAz71e6Y
out 15 21:06:46 servidor sshd-session[2931]: pam_unix(sshd:session): session opened for user ana(uid=1000) by ana(uid=0)
Sem o ssh-copy-id

Em sistemas sem ele, copie o conteúdo de ~/.ssh/id_ed25519.pub e cole numa linha nova de ~/.ssh/authorized_keys no servidor. Um comando faz tudo: cat ~/.ssh/id_ed25519.pub | ssh ana@192.168.0.50 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'.

Atalhos no ~/.ssh/config

Em vez de digitar usuário, IP, porta e chave toda vez, dê um apelido para cada servidor:

Host servidor
    HostName 192.168.0.50
    User ana
    Port 22
    IdentityFile ~/.ssh/id_ed25519

Host nuvem
    HostName 203.0.113.10
    User admin
    Port 2222

Agora ssh servidor e ssh nuvem funcionam, e os apelidos valem também no scp e no rsync (veja scp e rsync). O arquivo precisa ser só seu: chmod 600 ~/.ssh/config.

O root e o SSH no Debian

Abra a configuração efetiva do servidor (como root, o sshd -T mostra tudo o que está valendo):

#> sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication) '
pubkeyauthentication yes
passwordauthentication yes                « contas comuns podem entrar com senha
permitrootlogin without-password          « o root só entra com chave

without-password (o mesmo que prohibit-password) quer dizer que o root nunca entra por senha pelo SSH, mesmo digitando a senha certa:

$ ssh root@192.168.0.50
root@192.168.0.50's password:
Permission denied, please try again.
…
root@192.168.0.50: Permission denied (publickey,password).

O jeito do Debian é entrar com a sua conta e então virar root com su - (veja root, su e sudo):

$ ssh ana@192.168.0.50
ana@servidor:~$ su -
Senha:
root@servidor:~#
Mexer no sshd_config com cuidado

A configuração do servidor fica em /etc/ssh/sshd_config, e o Debian também lê os arquivos de /etc/ssh/sshd_config.d/ (vazia por padrão). Antes de recarregar, teste com sshd -t (sem saída = sem erro) e mantenha uma sessão aberta até confirmar que consegue entrar de novo. Como desligar a senha e outras proteções está em Segurança do Servidor.

Quando não funciona

Connection refused 
$ ssh ana@192.168.0.50
ssh: connect to host 192.168.0.50 port 22: Connection refused

O que aconteceu: a máquina respondeu, mas ninguém escuta na porta 22. O openssh-server não está instalado, o serviço está parado ou o SSH usa outra porta.

Como resolver: no servidor, systemctl status ssh; se faltar, apt install openssh-server. Se a porta for outra, use -p.

Connection timed out 
$ ssh ana@192.168.0.50
ssh: connect to host 192.168.0.50 port 22: Connection timed out

O que aconteceu: nada respondeu. O IP está errado, a máquina está desligada ou um firewall descarta os pacotes.

Como confirmar: ping -c 2 192.168.0.50 e, no servidor, as regras do firewall (veja nftables).

Could not resolve hostname 
$ ssh ana@servidro
ssh: Could not resolve hostname servidro: Name or service not known

O que aconteceu: o nome não existe (aqui, um erro de digitação) e não há apelido com esse nome no ~/.ssh/config.

Permission denied (publickey,password) 
$ ssh ana@192.168.0.50
ana@192.168.0.50: Permission denied (publickey,password).

O que aconteceu: o servidor recusou todas as formas de entrar que aceita (listadas entre parênteses). Senha errada, usuário errado, chave não instalada ou tentativa de entrar como root com senha.

Como investigar: ssh -v ana@192.168.0.50 mostra quais chaves foram oferecidas. No servidor, confira as permissões de ~/.ssh (700) e authorized_keys (600) e o log com journalctl -u ssh.

REMOTE HOST IDENTIFICATION HAS CHANGED! 
$ ssh ana@192.168.0.50
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!

It is also possible that a host key has just been changed.
The fingerprint for the ED25519 key sent by the remote host is
SHA256:2cYtXRUqFptnhM0jv3iLXRqpdarrvAHhWD8DsuQKQ5k.
Please contact your system administrator.
Add correct host key in /home/ana/.ssh/known_hosts to get rid of this message.
Offending ED25519 key in /home/ana/.ssh/known_hosts:3                       « linha 3 do arquivo
  remove with:
  ssh-keygen -f '/home/ana/.ssh/known_hosts' -R '192.168.0.50'           « o próprio comando para corrigir
Host key for 192.168.0.50 has changed and you have requested strict checking.
Host key verification failed.

O que aconteceu: o servidor apresentou uma chave diferente da guardada. O motivo comum e inofensivo: o servidor foi reinstalado, ou outro aparelho ganhou aquele IP. O motivo perigoso: alguém no meio do caminho.

Como resolver: se você sabe que o servidor foi reinstalado, apague a chave antiga e conecte de novo, conferindo a nova impressão digital:

$ ssh-keygen -R 192.168.0.50
# Host 192.168.0.50 found: line 3
/home/ana/.ssh/known_hosts updated.
Original contents retained as /home/ana/.ssh/known_hosts.old

Se você não sabe por que mudou, não conecte e investigue.

"ssh: comando não encontrado" no servidor? Não, "sshd" 
$ sshd -T
bash: sshd: comando não encontrado

O que aconteceu: o sshd fica em /usr/sbin, fora do PATH da usuária comum no Debian. Rode como root (su -).

Exercícios

1. Criar a chave

Complete para criar uma chave do tipo recomendado:

ssh-keygen -t

2. Instalar a chave no servidor

Complete com o comando que copia a chave pública para o servidor:

ana@192.168.0.50

3. Porta diferente

Complete para conectar na porta 2222:

ssh ana@servidor

4. No Debian, por que ssh root@servidor com a senha certa dá "Permission denied"?

5. A Ana procurou o servidor com grep 192.168.0.50 ~/.ssh/known_hosts e não achou nada, mas conecta sem a pergunta de primeira vez. Por quê?

Resumo

  • ssh usuario@maquina abre um terminal remoto; exit volta.
  • O servidor é o pacote openssh-server, serviço ssh; pode faltar se não foi marcado na instalação.
  • A primeira conexão pergunta pela impressão digital; confira com ssh-keygen -lf no servidor.
  • Chaves: ssh-keygen -t ed25519 e ssh-copy-id; permissões 700 e 600.
  • No Debian o root só entra por chave; entre com a sua conta e use su -.
  • Chave de máquina mudou? ssh-keygen -R, mas só se você souber o motivo.
